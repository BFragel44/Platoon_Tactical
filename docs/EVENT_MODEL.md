# Event Model

## Purpose

Platoon Tactical treats mission history as a first-class part of the simulation.

Every meaningful action, state change, discovery, and consequence during a
mission should produce a structured Event.

Events provide a single authoritative history of what occurred during a mission.

This history will eventually support:

- real-time UI updates
- combat visualization
- debugging
- mission statistics
- soldier histories
- campaign records
- after-action reports
- mission replay or reconstruction
- emergent narrative

The Event Model should be designed early because nearly every future game
system will depend on it.

---

# Core Principle

**The simulation determines what happened. Events record what happened.
Presentation systems interpret what happened.**

The UI does not determine combat outcomes.

Animations do not determine combat outcomes.

The AAR does not invent combat outcomes.

These systems consume Events generated by the authoritative simulation.

Example:

The simulation determines that an enemy machine gun attack causes Bravo Team
to become Pinned.

The simulation then records an Event representing that state change.

The command view may update Bravo's status marker.

A future close-up Location View may depict soldiers taking cover.

The audio system may play appropriate incoming-fire reactions.

The AAR may later report when and why Bravo became Pinned.

All of these presentations originate from the same simulation event.

---

# Event Philosophy

Events should represent meaningful facts rather than every internal calculation.

Record:

> Bravo became Pinned after receiving heavy machine-gun fire from Apartment 4.

Do not necessarily record every intermediate mathematical operation used to
reach that result.

The simulation may internally calculate:

- fire intensity
- weapon effects
- cover modifiers
- suppression values
- leadership modifiers
- morale checks
- random rolls

These calculations may be available in optional diagnostic/debug data, but the
primary Event history should remain understandable and useful.

Events should answer some combination of:

- What happened?
- When did it happen?
- Where did it happen?
- Who caused it?
- Who or what was affected?
- Why did it happen?
- What changed as a result?

# Event Requirements

Every Event must have a consistent core structure.

Exact implementation details may change during development, but an Event should
conceptually contain:

```text
Event
├── id
├── type
├── sequence
├── turn/time
├── location
├── actor
├── target
├── cause
├── result
└── metadata
```

Not every field is required for every Event.

For example, a mission-start Event may have no actor or target.

Core Event Fields
id

A unique identifier for the Event.

Example:

evt_000184

The exact identifier format is an implementation decision.

type

A stable machine-readable identifier describing what occurred.

Examples:

MISSION_STARTED
COMMAND_ISSUED
UNIT_MOVED
CONTACT_TRIGGERED
FIRE_OPENED
UNIT_PINNED
SOLDIER_WOUNDED

Event types should use consistent naming.

Event display text should not be used as the Event type.

sequence

A monotonically increasing value representing Event order.

This guarantees deterministic chronological ordering even when multiple Events
occur during the same turn or simulation timestamp.

Example:

181
182
183
184
turn/time

The point in the mission when the Event occurred.

During early prototypes this may simply be:

turn: 6

Future implementations may also contain simulation time:

turn: 6
mission_time: 00:08:42

The Event Model should not require real-time simulation.

location

The Location associated with the Event.

Prefer stable Location identifiers rather than relying only on display names.

Example:

location_id: loc_market_street

The Location may also have a human-readable name:

Market Street
actor

The entity primarily responsible for the Event.

Possible actors include:

soldier
team
leader
enemy unit
weapon
support asset
mission system

Example:

actor:
    type: TEAM
    id: bravo
target

The entity affected by the Event when applicable.

Example:

target:
    type: TEAM
    id: charlie

An Event does not require a target if none exists.

cause

Information describing what produced the Event.

Example:

cause:
    type: ENEMY_FIRE
    source_unit: enemy_hmg_02
    source_location: loc_apartment_4

Cause information is particularly important for later AAR reconstruction.

Knowing that Bravo became Pinned is useful.

Knowing that Bravo became Pinned because of HMG fire from Apartment 4 is much
more useful.

result

The meaningful state change produced by the Event.

Example:

result:
    previous_state: SUPPRESSED
    new_state: PINNED

Events should describe changes rather than requiring consumers to infer them
from unrelated data.

metadata

Optional additional structured information relevant to the Event.

Examples may include:

weapon used
ammunition expended
cover occupied
suppression amount
spotting quality
command cost
random roll
difficulty
distance/range
fire intensity

Metadata should not become an unstructured dumping ground.

Frequently used information should eventually become part of the formal Event
schema where appropriate.

Event Categories

Event types should be grouped conceptually by the system that generates them.

The categories below describe the expected direction of the game.

M0 only requires a subset.

Mission Events

Examples:

MISSION_STARTED
MISSION_ENDED
OBJECTIVE_REVEALED
OBJECTIVE_SECURED
EXTRACTION_STARTED
UNIT_EXTRACTED

For M0, only basic mission start/end Events are required.

Command Events

Examples:

COMMAND_ISSUED
COMMAND_COMPLETED
COMMAND_FAILED
COMMAND_CANCELLED

A command Event should record:

issuing leader/player
receiving unit
command type
command cost
target Location or target entity when applicable

Example concept:

COMMAND_ISSUED

actor: Platoon Leader
target: Alpha Team
command: MOVE
destination: Courtyard
cost: 1
Movement Events

Examples:

UNIT_MOVED
UNIT_ENTERED_LOCATION
UNIT_WITHDREW

For simple movement, M0 may use only UNIT_MOVED.

Movement Events should preserve both origin and destination.

Example:

UNIT_MOVED

unit: Alpha
from: Market Street
to: Courtyard
Contact Events

Examples:

CONTACT_TRIGGERED
CONTACT_RESOLVED
ENEMY_GENERATED
CONTACT_DETECTED
CONTACT_IDENTIFIED

These Events are critical to battlefield uncertainty.

The Event history should preserve the distinction between:

what actually existed in the simulation, and
what friendly forces knew at the time.

An enemy being generated does not necessarily mean that the player immediately
knows its identity or position.

Information and Fog of War

The Event Model must not accidentally destroy uncertainty.

The authoritative simulation history may contain information that was hidden
from the player at the time.

For example:

ENEMY_GENERATED
Enemy HMG Team
Apartment 4

may exist internally.

The player's visible history may instead initially contain only:

CONTACT_TRIGGERED
Possible enemy activity detected near Apartment 4.

Later:

CONTACT_DETECTED
Automatic weapons fire detected from Apartment 4.

And eventually:

CONTACT_IDENTIFIED
Enemy HMG Team identified in Apartment 4.

Therefore, systems consuming Events must respect information visibility.

A future AAR may intentionally reveal information that was unknown during the
mission, but the live tactical interface must not gain omniscient knowledge
simply because the authoritative Event exists.

Spotting Events

Examples:

CONTACT_DETECTED
UNIT_SPOTTED
UNIT_IDENTIFIED
CONTACT_LOST

Spotting Events should record:

observer
observed entity
Location
resulting information state

M0 does not require an elaborate detection model.

Fire Events

Examples:

FIRE_OPENED
WEAPON_FIRED
FIRE_SHIFTED
FIRE_CEASED

Fire Events should eventually allow the mission history to answer:

who fired
at whom or where
with what weapon
from what Location
toward what Location
when fire began
when fire stopped or shifted

Not every individual bullet needs its own Event.

Automatic weapons should generally generate meaningful bursts or firing actions
rather than hundreds of bullet Events.

Suppression and Morale Events

Examples:

SUPPRESSION_CHANGED
UNIT_SUPPRESSED
UNIT_PINNED
UNIT_BROKEN
UNIT_RALLIED

State-transition Events are especially important.

For example:

UNIT_PINNED

target: Bravo Team
location: Market Street

cause:
    enemy: Enemy HMG Team
    location: Apartment 4

result:
    previous_state: SUPPRESSED
    new_state: PINNED

This provides enough information for both gameplay presentation and later
narrative reconstruction.

Cover Events

Examples:

COVER_SEARCHED
COVER_FOUND
COVER_SEARCH_FAILED
UNIT_ENTERED_COVER
UNIT_LEFT_COVER

Cover discovery is persistent within a mission.

A COVER_FOUND Event should identify:

searching unit
Location
discovered cover
relevant properties

Example:

COVER_FOUND

actor: Alpha Team
location: Residence

cover:
    type: CONCRETE_STAIRWELL
    protection: 2

The discovered cover becomes part of the persistent mission state.

Casualty Events

Future versions may include:

SOLDIER_WOUNDED
SOLDIER_INCAPACITATED
SOLDIER_KILLED
SOLDIER_STABILIZED

Casualty Events should identify individual soldiers even though battlefield
commands primarily operate at team level.

This is necessary for persistent personnel histories and meaningful AARs.

Example:

SOLDIER_WOUNDED

target: Cpl. David Hayes
team: Bravo
location: Hotel 2F

cause:
    weapon: RPG
    source_location: East Rooftops

M0 may use a simplified casualty model.

Objective and Extraction Events

These systems are outside M0 but the Event Model should anticipate them.

Examples:

OBJECTIVE_SECURED
VIP_RECOVERED
VIP_LOST
EXTRACTION_STARTED
EXTRACTION_ZONE_REACHED
UNIT_EXTRACTED
UNIT_LEFT_BEHIND

These Events will eventually allow the game to reconstruct complex mission
outcomes without scripted narrative sequences.

Event Chains

Important battlefield moments will often consist of multiple related Events.

Example:

COMMAND_ISSUED
    ↓
UNIT_MOVED
    ↓
CONTACT_TRIGGERED
    ↓
ENEMY_GENERATED
    ↓
CONTACT_DETECTED
    ↓
FIRE_OPENED
    ↓
SUPPRESSION_CHANGED
    ↓
UNIT_PINNED

Events should therefore support optional relationships such as:

parent_event_id
caused_by_event_id

This allows later systems to reconstruct causality.

For M0, a simple caused_by_event_id relationship is sufficient if event
linking is implemented.

Avoid building a complex event graph before it is needed.

Example Event

The exact code representation will be determined during architecture design.

Conceptually:

{
  "id": "evt_000184",
  "type": "UNIT_PINNED",
  "sequence": 184,
  "turn": 12,
  "location_id": "loc_hotel_2f",
  "actor": {
    "type": "ENEMY_UNIT",
    "id": "enemy_hmg_02"
  },
  "target": {
    "type": "TEAM",
    "id": "bravo"
  },
  "cause": {
    "type": "AUTOMATIC_FIRE",
    "weapon_id": "hmg_02",
    "source_location_id": "loc_market_north"
  },
  "result": {
    "previous_state": "SUPPRESSED",
    "new_state": "PINNED"
  },
  "metadata": {
    "fire_intensity": "HEAVY"
  },
  "caused_by_event_id": "evt_000181"
}

This example illustrates intent only.

It does not define the final implementation schema.

After-Action Reports

The AAR is a consumer of the Event history.

It should not maintain an independent version of mission history.

For M0, the AAR may simply transform Events into chronological human-readable
entries.

Example:

TURN 4
Alpha Team moved from Market Street into the Courtyard.

Alpha triggered a Potential Contact in the Courtyard.

Enemy activity was detected.

Enemy automatic weapons fire opened from the Residence.

Alpha became Suppressed.

Alpha searched for cover and discovered a masonry wall.

Alpha occupied the masonry wall.

Alpha rallied and returned to Effective status.

Future AAR systems may produce:

timelines
maps
casualty summaries
ammunition reports
soldier performance records
command histories
mission statistics
campaign history
narrative summaries

All should derive from the same Event history.

Emergent Narrative

The Event Model should allow important stories to be discovered after they
occur rather than explicitly scripted beforehand.

For example, a future mission history might establish that:

Charlie Team recovered a VIP.
Enemy contacts appeared along the extraction route.
Charlie became Pinned.
Bravo occupied strong multistory cover.
Bravo's surviving automatic weapon suppressed the enemy position.
Charlie recovered and moved toward extraction.
Bravo received additional enemy fire.
Bravo requested danger-close air support.
Charlie reached the extraction point.
Bravo never extracted.

No Event needs to say:

BRAVO_HEROICALLY_SACRIFICED_ITSELF

That meaning emerges from the sequence and context of ordinary simulation
Events.

This is the intended foundation of Platoon Tactical's storytelling.

Determinism and Randomness

Random outcomes should be reproducible when practical.

Mission state should eventually retain the random seed used by the simulation.

This will help with:

debugging
automated testing
balance testing
reproducing unusual outcomes
validating AAR accuracy

M0 should prefer deterministic seeded randomness if it can be implemented
without unnecessary complexity.

Debug Information

Development builds may expose additional Event information that the normal
player interface does not show.

Examples:

random roll
probability
modifiers
hidden enemy identity
suppression calculation
spotting calculation

This information is useful for validating the simulation.

Debug information must remain separate from player-visible information so that
development tools do not dictate final UI design.

M0 Required Event Set

Milestone 0 should begin with the smallest useful Event vocabulary.

Initial candidates:

MISSION_STARTED
TURN_STARTED

COMMAND_ISSUED

UNIT_MOVED

CONTACT_TRIGGERED
ENEMY_GENERATED
CONTACT_DETECTED

FIRE_OPENED
FIRE_CEASED

SUPPRESSION_CHANGED
UNIT_SUPPRESSED
UNIT_PINNED
UNIT_RALLIED

COVER_SEARCHED
COVER_FOUND
COVER_SEARCH_FAILED
UNIT_ENTERED_COVER

SOLDIER_WOUNDED
SOLDIER_KILLED

ENGAGEMENT_RESOLVED
MISSION_ENDED

This list is not immutable.

Events should be added when the simulation needs to communicate a meaningful
fact, not merely because a hypothetical future system might use them.

Scope Guard

Do not build a generalized enterprise event framework.

The Event Model exists to support a tactical game.

For M0:

an in-memory ordered Event collection is sufficient
complex event sourcing infrastructure is unnecessary
databases are unnecessary
networking concerns are unnecessary
replay UI is unnecessary
AI narrative generation is unnecessary

The architecture should remain simple enough to change as the combat model is
discovered.

The immediate goal is:

At the end of an M0 firefight, can the game accurately explain what happened,
in what order, where it happened, who was involved, and why the important
state changes occurred?

If it can, the Event Model is doing its job.


I especially want to preserve the **fog-of-war section**. That's an architectural issue that could bite us badly later: the simulation needs to know that an HMG team exists while the player's UI may know only that *something is firing from that building*. If we don't establish that distinction early, the event log can accidentally become an omniscience leak.

The other line I'd consider almost sacred is:

> **No Event needs to say `BRAVO_HEROICALLY_SACRIFICED_ITSELF`.**

That's essentially the philosophy behind the AAR system we're envisioning. The game records facts.
